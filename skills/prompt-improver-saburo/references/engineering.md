# 工学的な具体化

すべてを毎回プロンプトに入れるな。以下から、要求やコードに根拠がある観点を選び、判断と検証へ変換せよ。一般原則から業務仕様の答えを捏造するな。

## 要求と設計を混ぜない

「CSVを比較し差分を出す」は要求、「辞書で索引を作る」は設計案。「速くする」は目標であり、データ量、基準実測、許容時間が分からなければ数値要件ではない。まず利用者が何を観測できれば成功かを決め、設計案はその理由とともに示せ。

| 該当する状況 | 明確にすること | 検証へ落とす例 |
| --- | --- | --- |
| 入力を受け取る | 形式、型、範囲、必須、空・欠損・不正の区別。補正か拒否か | 空入力、境界値、不正形式で観測可能な結果 |
| 集計・比較・変換 | キー、順序、重複、丸め、文字コード、単位、時刻の扱い | 既知の小例で期待結果を手計算し、同値・境界を確認 |
| データが増える | 入力規模、処理量とメモリ、最悪条件、ボトルネック | 同条件の変更前後比較。平均だけでなく尾部が必要か判断 |
| 状態を更新する | 更新主体、不変条件、原子的な範囲、部分失敗、同時更新 | 途中失敗で壊れないか、二重実行や競合で何が残るか |
| 外部API・非同期処理 | 期限、キャンセル、再試行可能な失敗、回数・総時間の上限 | タイムアウト、一時失敗、永続失敗で終了できるか |
| 再送・Webhook・ジョブ | 重複識別、冪等性、順序逆転、再開位置 | 再送・再起動・順不同でも副作用が要求どおりか |
| ファイル・CLI | パス、既存ファイル、破損、標準出力と標準エラー、終了コード | 上書き条件、途中失敗、空白や非ASCIIのパスを確認 |
| 認証・権限・公開API | 信頼境界、認証と認可、対象資源へのアクセス制御 | 未認証、権限不足、別利用者の資源へのアクセス |
| ユーザー入力を実行先へ渡す | SQL・シェル・HTMLの境界、パラメータ化、出力先制限 | 特殊文字がコードとして実行されないか |
| 画面・対話 | 主要操作、入力エラー、空・待機・失敗状態、キーボード操作 | 操作シナリオ、表示・フォーカス・状態遷移 |
| API・スキーマを変える | 利用者、既存入力・出力、移行期間、互換性の範囲 | 旧クライアント・旧データと新実装の組合せ |
| 依存を追加・更新 | 必要性、既存代替、対応版、配布条件、既知の脆弱性 | ロック情報、構築再現性、互換テスト |
| 運用・長時間処理 | 失敗を検知する情報、機密を除くログ、停止・再開、資源解放 | 失敗を成功表示しないか、ログで原因を絞れるか |
| インフラ・IaC | 実状態と管理状態、差分、対象環境、依存と適用順序 | validate/plan等の意味を確認し、実適用とは区別 |

## 原則を具体的な選択へ変える

- **単純性・必要性**: 今の要求を満たす最小構成を選ぶ。将来のためだけのマイクロサービス、プラグイン機構、汎用フレームワークは加えない。
- **責務分離・凝集度**: 入出力、業務判断、副作用が別の理由で変わるなら境界を置く。すべてをクラスへ分解するという意味ではない。
- **結合度・依存方向**: テストや変更が外部API・DB・時刻に引きずられるなら境界を切る。対象が小さく固定的なら、不要なインターフェースを増やさない。
- **重複の整理**: 同じ業務知識が複数箇所で不整合になるなら集約する。似た構文だけで共通化しない。異なる変更理由まで結合する抽象化は避ける。
- **明示性**: 型、名前、不変条件、エラーの区別で読み違いを減らす。「nullなら適当に初期化」「例外はすべて成功扱い」を指示しない。
- **変更可能性**: まず既存の構造で成立するか検討する。大きな設計変更は、減らせる具体的な問題と移行費用を示して判断する。
- **測定**: 最適化や可用性向上は、負荷・期間・環境・計測方法を揃える。測っていない改善率を成果にしない。

## 目的別に重点を変える

新規開発は最小の利用シナリオと入出力を決め、動く縦断部分から検証する。障害修正は再現と原因を優先し、周辺の全面改修を混ぜない。リファクタリングは維持する観測可能な動作を先に定め、機能変更と区別する。レガシー改修は実際の動作を記録するが、既知の不具合を新しい正しい仕様として固定しない。

テストは要求の誤りまで自動的に正せない。実装者と同じ思い込みからテストを作らないよう、公開仕様、利用者のシナリオ、既知の小例、守るべき性質を根拠にする。被害の大きい箇所ほど独立した視点が必要だが、外部レビューの依頼やエージェント起動は実行環境の許可に従う。
