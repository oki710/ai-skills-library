# 例と失敗例

## 軽量: 指定された文言だけ

原案: 「保存ボタンを『登録』にして。APIや画面レイアウトは変えない。プロンプトだけ短く」

完成例:

```text
対象画面の保存ボタンの表示文言を「登録」に変更してください。API、処理、画面レイアウトは維持してください。対象の表示定義と既存の確認方法を調べ、変更後の文言と表示崩れがないことを確認し、差分と確認結果を短く報告してください。
```

設計書、全E2E、依存追加を要求しない。実際の画面を見ていないなら対象画面名を創作しない。

## 標準: API再試行の障害修正

原案: 「送信処理がたまに失敗する。リトライをいい感じに。二重登録は困る」

生成する指示は、まず失敗の種類、送信先仕様、処理の副作用、現在の再試行を調べるものにする。「3回なら安全」や「あらゆるPOSTを再送」と確定しない。応答を受け取れなかった場合にもサーバー側が成功している可能性を扱い、重複抑止が成立するか確認する。バックオフだけで二重登録は防げない。

受入条件の例は、正常時、一時失敗後の成功、再試行対象外の失敗、上限到達、重複送信。具体的な上限は確認済み仕様か提案として分ける。

## 慎重: データ移行

原案: 「旧テーブルを削除して新形式へ。顧客データは失わない。改善して実行」

データ保存と削除の両方を残し、読取調査、移行案、互換期間、照合、バックアップと復元可能性、切替条件を具体化する。対象環境や承認が不明な本番削除は実行しない。安全な準備とテストは進める。「git revertでデータ復旧」と書かない。

## 意味を壊す典型

| 原案 | 誤った改善 | 保持すべき意味 |
| --- | --- | --- |
| 最大3回再試行 | 合計3回まで試行 | 初回とは別に再試行が最大3回。上限の対象を確認 |
| 失敗した場合だけ通知 | 成否を通知 | 成功通知を追加しない |
| UTCで保存、日本時間で表示 | すべて日本時間 | 保存と表示の境界を維持 |
| 既存APIを変えずに追加 | APIを整理して統一 | 互換性条件を保持 |
| 速くなると思う | 性能が向上する | 仮説のまま測定計画へ |
| テストが通ったと報告された | テスト実施済み | 伝聞と自身の実行証拠を分ける |
| 調査だけ、変更禁止 | ログ追加と再起動で調査 | 書込みや再起動を加えない |
| 古いレコードを削除 | 30日より前を削除 | 「古い」の業務定義を確認。数値を発明しない |

## 相反する要求

「全件を厳密に一意化、順序保持、任意に大きい入力、追加メモリは固定、外部保存禁止」は、入力とモデルによって同時に満たせない。まず制約を明示し、許容できる入力上限、外部保存、近似のどれを選べるか確認する。実現不能な計算量を保証しない。
