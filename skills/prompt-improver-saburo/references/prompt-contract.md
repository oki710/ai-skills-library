# 出力と引継ぎ

## 完成版の組み立て

次の材料を必要な分だけ使い、原案にない機能や数値で埋めない。表記修正なら一段落でよい。読み手が判断できる密度を保ち、長いテンプレートの空欄埋めを目的にしない。

```text
{対象}について、{実行する工程}を行ってください。
目的は{利用者が得る結果}です。

現状・入力:
{確認済みの状態、提供資料、実行時に確認すること}

要求・制約:
{必要な動作、数量、例外、互換性、対象外、変更禁止箇所}
{提案や仮定は要求とは区別して記載}

進め方:
{必要な現状確認、設計判断、最小実装、適切な検証}
{必要なときだけ失敗時の扱い、停止・復旧、承認境界}

受入条件:
{条件・操作・観測結果。関係する異常系と保持する動作も含める}

成果物・報告:
{コード/差分/設計/レビューなど依頼された成果物}
{実施した検証と未実施、残る課題を区別して報告}
```

`{対象}` などの変数は別案件で入力が必要な箇所だけに残す。すでに分かっている情報は埋める。コマンド・パス・受入値が不明なら、実行時の確認方法に置き換える。APIキーは具体値を再掲せず「既存の安全な認証設定を使用」と書く。

## 単独利用と工程の引継ぎ

改善した本文を別環境へ渡しても使えるよう、意味のある条件をスキル名や「同上」に逃がさない。対象資料が添付・リポジトリにあるなら、どれを読むかを指定する。別工程への引継ぎは以下を必要な範囲で含める。

| 引き継ぐ情報 | 内容 |
| --- | --- |
| 対象 | リポジトリ・版・関連ファイル。未確認ならその旨 |
| 要求 | 完成版の要求と受入条件。保留・提案を区別 |
| 決定 | 採用した方式、理由、維持する互換性 |
| 証拠 | 再現、差分、実施テスト、残る失敗 |
| 権限 | 実行可能な範囲、禁止範囲、確認が残る操作 |
| 次の工程 | 何をすれば次の状態へ進めるか |

「引継ぎ作成済み」は「実装済み」ではない。実行依頼がある場合、引継ぎ文の提示で止めず、実行可能な次工程へ進む。

## 文章の具体性

「エラーハンドリングを強化する」では対象・失敗・返り値が分からない。例として「一時障害だけを上限付きで再試行し、最終失敗を呼出元へ返す」とする。ただし、一時障害の定義と上限は現行仕様から確認するか提案として扱う。

「網羅的にテストする」では合否が分からない。「通常の更新、重複依頼、権限不足、保存失敗を確認し、失敗時に一部だけ保存されないことを確かめる」のように対象を具体化する。無関係なケースを足さない。

「高品質・安全・保守可能」は評価語であり、その語を増やしても仕様にならない。読み手が迷う箇所を、条件・主体・操作・結果の対応で解消する。自然に読める文を一律に短文化せず、必要な箇条書きや表は残す。
