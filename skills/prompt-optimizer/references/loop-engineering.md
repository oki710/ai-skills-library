# ループエンジニアリング

確認日：2026-10-27。

Loop Engineeringは、AIエージェントへ毎回人が次の指示を与える代わりに、目標へ向けて **act → observe → decide/adjust** を反復できる実行系を設計する考え方です。IBMは2026年7月、ユーザー定義のGoalへ向けてエージェントを反復的に導くagentic workflowとして整理しています。

この資料では、プロンプトを長くすることではなく、**検証可能な制御ループを小さく設計すること**を目的とします。

## いつ使うか

次のいずれかがある場合に候補とします。

- 実行結果を見ないと次の操作を決められない
- テスト、lint、build、差分、ログなど、反復ごとにVerifierを実行できる
- 調査→仮説→確認→修正の循環が必要
- 長い作業で、途中状態や未解決事項を残して再開する必要がある
- 独立した作業を並列化し、最後に統合・再検証する価値がある

要約、翻訳、定型変換、明確な1ファイル修正など、1回で完了できる依頼には原則使いません。

## ループ契約

必要な項目だけ定義します。

| 要素 | 設計する内容 |
|---|---|
| Goal | 利用者から見て何が完成すれば成功か |
| State | 次の反復へ持ち越す確認済み事実、差分、未解決事項 |
| Act | 1回の反復で行う小さな操作 |
| Observe | コマンド結果、ログ、差分、画面、API応答など取得する事実 |
| Verify | Goalへの適合をどう判定するか |
| Adjust | 観測結果ごとに仮説・操作をどう変えるか |
| Stop | 成功、失敗上限、危険増大、承認待ちで停止する条件 |
| Budget | 必要なら最大試行、時間、費用、並列数 |
| Escalate | 人間の判断が必要になる条件と、渡す証拠 |

## Verifierを先に置く

反復の品質は「何回考えるか」より、**何をもって改善と判定するか**で決まります。

可能なら次を優先します。

1. 既存テスト、回帰テスト
2. lint、format、型検査、構文検査
3. build、CI、dry-run、plan
4. 期待入出力との比較
5. 実測、ログ、メトリクス
6. 差分レビュー、公開仕様との照合
7. ほかに証拠がない場合の自己レビュー

自己評価だけで成功を断定せず、Verifierそのものが要求を表しているかも確認してください。テストを削除したり、assertionを弱めたり、エラーを握りつぶして成功を作りません。

## Adjustment policy

失敗時は、同じ操作をそのまま再実行する前に観測結果を分類します。

- **入力・前提が誤り**：対象、版、パス、再現条件を確認し直す
- **実装が要求不適合**：最小差分で修正し、同じVerifierを再実行する
- **Verifierが誤り**：要求との対応を説明できる場合だけ修正する
- **一時的な外部失敗**：再試行可能性と副作用を確認し、上限付きで再試行する
- **権限・承認不足**：無理に迂回せず停止し、必要な承認と影響を示す
- **新しい情報が得られない**：ループを止め、確認済み事実と次の判定方法を残す

## 停止条件

「成功するまで」「完璧になるまで」「問題がなくなるまで」は停止条件ではありません。

最低でも次を区別します。

- **Success**：受入条件と必要なVerifierが満たされた
- **Bound reached**：最大試行、時間、費用などの上限に達した
- **No progress**：新しい証拠が増えず、同じ失敗を繰り返している
- **Risk increased**：破壊的変更、秘密、外部送信、本番影響などへ範囲が広がる
- **Approval required**：ユーザーや運用責任者の判断が必要
- **Environment blocked**：必要なツール、権限、接続がない

停止した場合は「失敗」で終わらせず、現在地、実施済み、未解決、次の安全な確認方法を残します。

## 並列化

並列AgentやSubagentは、独立性がある場合だけ使います。

向いている例:

- コード調査と公式仕様調査
- 複数の独立モジュールの読み取りレビュー
- 実装と、変更権限を持たない独立Verifier
- 複数案の比較

避ける例:

- 同じファイルを複数Agentが同時編集
- 前段の結果へ強く依存する作業の無理な並列化
- 統合担当や競合解消条件がない分割

親Agentは、子の結論をそのまま採用せず、入力条件、証拠、矛盾、統合後のVerifierを確認します。

## 状態と再開

長時間作業では、逐語的な思考履歴ではなく、再開に必要な事実を残します。

```text
Goal:
Current state:
Completed:
Verified:
Open issues:
Last failure:
Next action:
Stop/approval conditions:
```

状態は正本を1つにし、チャット、README、TODOなどへ同じ情報を重複させすぎません。

## 典型的な失敗

- 単発タスクを無意味にループ化する
- 「自己改善」「自己反省」をVerifierなしで何度も回す
- 無制限の試行、token、時間、外部API呼出しを許す
- 失敗したテストを消して成功扱いにする
- 同じエラーへ同じ操作を繰り返す
- Subagentを増やし、統合コストの方が大きくなる
- 状態を持ちすぎて古い仮定を事実として再利用する
- 本番変更や外部送信まで「ループの続き」として無断で広げる
