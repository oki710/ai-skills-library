# テストとデバッグ

## 合否を実装の外から決める

期待値をユーザーの要求・公開仕様・障害再現・手で追える小例から決める。実装の式をテストにコピーするな。内部の呼出回数だけを確認して外から見た動作を未確認にするな。

| 変更・リスク | 選ぶ検証 |
| --- | --- |
| 表記・設定の局所変更 | 差分、構文、実際の表示や読込み。無益な単体テストは足さない |
| 純粋な計算・変換 | 小さな既知例、境界、同値クラス、必要なら性質のテスト |
| DB・ファイル・外部サービス境界 | 単体に加え、対象境界の結合・契約確認 |
| 利用者の重要な操作 | 少数の実際の操作経路、必要ならE2EとUI確認 |
| 認可・入力処理 | 権限不足、別利用者、不正入力、情報漏えいを起こす失敗経路 |
| 競合・再試行 | 重複、順序逆転、途中失敗、回数と総時間の上限 |
| データ移行 | 旧新データ照合、再実行、部分失敗、復元または前進修復 |
| 性能 | 基準状態と同じ条件での負荷・時間・資源測定 |

テストの層や件数を固定比率にしない。変更範囲で失敗を検出できる最も軽い方法を選び、外部境界の不確実性が残るときに上位の検証を加える。カバレッジの数値だけで正しさを保証しない。

## 障害修正

1. 症状、影響、観測時刻、再現条件、直近変更を確認する。まず読取りや影響の小さい確認を選ぶ。
2. 正常例と異常例を比較し、入力から結果まで境界を追う。観測事実と原因候補を分け、候補を確かめる最小の確認を選ぶ。
3. 可能なら失敗する回帰テストを作り、目的の不具合で失敗することを確認する。既存の失敗も記録する。
4. 原因に対応する最小修正を行い、回帰テストと影響する既存テストを実行する。修正前のコードを削除してTDDの順序を作り直す必要はない。
5. 再現できなければ、その限界と確認できた範囲を示す。時間依存なら制御できる時刻や同期条件を使い、根拠のないsleep延長で通さない。

緊急の被害抑制は根本修正と区別する。原因未確定でも承認済みの可逆な緩和策が必要な場合は、根拠・限界・監視・戻し方を示して実行し、原因を特定済みと呼ばない。

## テストの信頼性

モックは境界の制御に使い、外部サービスと互換であることの証明には使わない。時刻・乱数・ネットワーク依存を固定できる箇所では再現性を確保する。既知の不具合を「現状だから正しい」と期待値に固定しない。

無関係な既存テストの失敗を無視せず、今回の変更によるものか切り分ける。環境不足、認証不足、レート制限による未実施をテスト合格に数えない。フレークを再実行で隠さず、頻度と条件を記録する。

仕様適合レビューでは要求の欠落・余分な機能・互換性を確認する。品質レビューでは複雑さ・失敗経路・権限・テストの検出力・依存を確認する。重大な欠陥と好みの指摘を区別し、自己レビューの限界を明示する。

## 証拠の残し方

小さな作業は「実施した確認と結果」で十分。複数要件では次の表を必要に応じて使う。

| 要求 | 検証方法・環境 | 観測結果 | 判定 |
| --- | --- | --- | --- |
| 要求の識別子または短い文 | 実際に実行したコマンドや操作 | 実際の件数・エラー・状態 | 合格／不合格／未実施 |

ログには必要な証拠だけを残し、秘密値を含めない。テスト実施日時や対象版が意味を持つ場合は併記する。長いログをそのまま最終回答へ貼らない。
