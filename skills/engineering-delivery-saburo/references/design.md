# 設計と実装の判断

要求に関係する部分だけを決める。設計書の有無を設計品質の代用にしない。

## 現状を読む

変更箇所だけでなく、入力元、出力先、呼出元、保存形式、関連テストを追い、変更が守る契約を特定する。実装と文書が食い違えば、どちらを観測したかを記し、正しい業務仕様を勝手に決めない。ユーザーの未コミット変更は上書き・reset・cleanしない。

## 設計を確かめる質問

| 観点 | 判断と実装への反映 |
| --- | --- |
| 責務 | 入出力、業務判断、副作用のうち、別の理由で変わる部分に境界を置く |
| 型と不変条件 | 未入力・不正・空・ゼロを区別し、壊れてはいけない関係を定める |
| データ構造と計算量 | 必要な検索・更新・順序に合う構造を選び、最大入力での時間・メモリを見積もる |
| 状態と整合性 | 誰が更新するか、原子的に成功すべき範囲、部分失敗、並行更新を扱う |
| インターフェース | 入力、戻り値、エラー、互換性を明示し、呼出元への影響を確認 |
| 副作用と資源 | ファイル・接続・ロックを確実に解放し、取消・途中終了の状態を扱う |
| 依存 | 既存ライブラリや標準機能で十分か。追加の保守費用と互換性を確認 |
| セキュリティ | 信頼境界で検証し、認証と対象資源への認可を分ける。秘密をログやエラーへ出さない |
| 観測可能性 | 障害を切り分ける最小限の識別情報と結果を残す。機密ペイロードの全出力を避ける |

SOLID、DRY、KISS、YAGNI等は判断の手掛かりとし、適用そのものを目的にしない。実際に異なる責務があるなら分離し、同じ知識が二重管理されるなら集約する。似たコードというだけの共通化、単発処理への過大な抽象化を避ける。

## 実装の進め方

新規開発では、主要な入力から結果まで動く最小単位を作り、後から境界を広げる。既存改修では、公開インターフェースを保ち、変更対象の最小範囲から進める。リファクタリングでは、維持する振る舞いを先に記録し、機能追加と分離する。

検証のための差し替え口は、時刻・外部通信・乱数・永続化など具体的な理由がある箇所へ置く。テストのためだけに公開APIを増やさない。エラーは呼出元が判断できる単位で区別し、広い例外捕捉で不具合を成功扱いにしない。

性能問題では先に同条件で測り、ボトルネックを絞る。キャッシュを追加するなら無効化、容量上限、古い値の許容を設計する。並列化なら競合、順序、上限、キャンセルを扱う。測定しないまま高速化を断言しない。

重要な方式選択は、課題、採用案、主な代替、判断理由、残るリスクを短く残す。既存方式で十分なら複数案を水増ししない。
